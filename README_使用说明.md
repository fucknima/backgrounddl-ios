# BackgroundDL 1.5 · 分享链接与精简下载页

## Safari / 第三方浏览器分享

打开任意 HTTPS 网页 → 系统分享按钮 → 选择「后台下载」→ 分享扩展提示已接收。
打开 BackgroundDL 主 App，会自动切换到浏览器、加载分享网页；从网页点击下载按钮后才进入系统后台下载任务。分享扩展本身不会擅自开始下载，也不保证自动拉起主 App（iOS 不为 Share Extension 保证这个能力）。

## 签名与 App Groups（必须阅读）

新增 `BackgroundDLShareExtension.appex`，与 Live Activity 扩展一起包含于 IPA。
主 App bundle ID `com.example.backgrounddl`、分享扩展 bundle ID `com.example.backgrounddl.share`；两者需要用同一开发团队签名，**并为两者开启完全相同的 App Group：** `group.com.example.backgrounddl.shared`。该 Group ID 必须在 Apple Developer 中注册并允许写入对应的 Provisioning Profile；签名前如果更改 Bundle ID，要同步更改两个 entitlements 文件、共享收件箱类和分享扩展中的 group 字符串。没有匹配 App Group 授权的个人签名/证书，可能安装失败或分享虽打开但数据不能传到主 App。禁止通过私有 API 强制从扩展拉起主 App。

## 下载页设计

去掉顶部大卡片与任务大卡片。保留一行总览、一个系统分段筛选、紧凑的文件行与细进度条。点击“···”、长按或左滑执行暂停、继续、删除、重命名或分享。默认“删除”只清理记录，不自动删已完成文件；显式选择“删除文件和记录”才删除本地文件。

## 保留的功能

- 普通网页内点击下载，交由系统后台 URLSession；已完成文件在「文件 → 在我的 iPhone 上 → 后台下载 → Downloads」。
- 速度与 ETA、灵动岛及锁屏 Live Activity。
- 自动深色网页与深色 App 图标。
- 大文件断点数据（由服务器支持情况决定），不可保证系统后台始终满速。

## 编译

推送到 main 自动触发 GitHub Actions，输出 `BackgroundDL-unsigned.ipa`。IPA 为未签名包，需签名主 App、Live Activity 和 Share Extension；不要只签主 App。

## 1.9（合并 1.7～1.9）稳定性、界面与智能高速

- 断点文件单独保存于 `Application Support/Resumes`，不再嵌入整个下载 JSON，降低大文件暂停后写盘负担。更新任务进度时数据库节流，每隔数秒持久化一次；状态切换仍立即持久化。
- 标准系统下载完成后先把 URLSession 临时文件移到 `Staging`，再在应用主线程执行文件名冲突检查和落盘。`finalizations.json` 帮助恢复移动文件后、数据库状态更新前的异常退出；启动时会扫描暂存完成文件。
- 完成文件进行实际字节长度检查；仅长度校验不能替代 SHA-256 校验，服务器没有提供可信哈希值时不可声称校验了文件内容。
- 仅网络超时/连接丢失/离线等可恢复错误，对**普通直链**自动重试最多 3 次，采用递增延迟；App 在后台挂起时不保证定时器按时执行，重新启动会重新调度尚未执行的重试。网页登录的临时下载链接不盲目自动重试。
- 下载列表增加搜索、排序（名称、时间、文件大小）、完成文件快速预览；“下载模式”入口提供稳定后台/智能高速/极速分段三档，完成/失败通知需用户自行开启权限。
- **智能高速模式只对普通 HTTPS 直链生效**：先 HEAD 查询大小及 Range 能力，再实际请求 1 字节验证 `206 Content-Range`，同时要求 ETag 或 Last-Modified 验证器；不支持或空间不足则回退为普通后台单任务。2 路（智能）或 4 路（极速）下载任务全部交由系统后台 URLSession；每段必须验证 206、范围、长度，出错拒绝合并。
- 分段以系统后台下载任务完成后落盘，再以 1 MiB 有界缓冲合并。逐段同步写入合并进度，已成功合并的块才能被清理，意外中断后可尝试恢复。合并时至少需要部分额外空间；建议预留大于文件大小的 125%～150% 空间。
- iOS 最终控制后台调度，分段不能保证后台速度超过单任务；不同服务器有并发限制，甚至会限速。**当前仅完成代码测试和 Xcode 编译测试，20GB 实机长时间传输、网络切换和分段合并仍需真实测试**。
- 不修改数据目录/Bundle ID，不删除现有文件；对上一版进行覆盖安装通常可保留数据，但切勿在大型任务正在传输时更新应用。

## 可靠性回归测试

## 1.9.1 · 修复左滑删除确认弹窗闪退

- 删除确认状态不再挂在可复用的下载列表行，而是由下载页面统一管理，避免滑动行被系统收起时弹窗同时销毁。
- 左滑“删除”只提交请求，关闭全滑即删的隐式行为，待用户确认后才通过 UUID 删除任务。
- 菜单、长按、左滑复用同一套删除确认逻辑；已完成文件默认只删除记录，不误删本地文件。
- 不修改后台传输核心及已有任务数据库格式，升级保留现有下载任务。

## 1.9.2 · 删除确认弹窗精准锚定修复

- 单任务“删除”与“移除记录”的确认弹窗现使用附着于目标下载行的 SwiftUI 原生 `popover`，包括 iPhone 紧凑布局强制使用 Popover，不再出现在下载页顶部的工具栏附近。
- 页面仍统一持有待删除任务 UUID，左滑不允许全滑删除；操作按钮先退出滑动/菜单动画，再呈现目标行锚定的确认弹窗。
- 用户确认后先关闭 Popover，待退出动画完成再按 UUID 删除记录或文件，避免弹窗消失时同时销毁列表行导致崩溃。
- 批量清理继续使用工具栏页面级确认弹窗；单文件删除仍默认仅移除记录，不会直接删除本地文件。
- 这次只改变界面交互，不改变已有下载任务数据库、后台 URLSession 或分段状态。

## 1.9.3 · 修复左滑删除后本地文件残留

- 修复已完成条目左滑“删除”过去只移除记录、不删除文件的错误：现在左滑删除已完成任务会请求永久删除实际文件和记录，需要明确确认。
- 保留“仅移除记录”作为独立菜单选项，不影响已下载文件。
- 下载页右上角「···」增加“本地文件管理”，直接展示 Downloads 文件夹里的实际文件（包含旧版已经移除记录但遗留的文件），支持预览及永久删除。
- 删除文件失败时不移除下载记录，严格校验文件确实已不在磁盘。对已删除记录造成的孤立文件可在“本地文件管理”中清理。
- 保留 1.9.2 下载行锚定的 Popover 与左滑二次确认，不改后台会话和文件数据库格式。

## 1.9.4 · 全新浅色/深色图标

## 2.0 · 原生任务详情、文件中心、浏览器主页和设置

- 顶部界面保持 iOS 原生样式，底部四个栏目：浏览器、下载、文件、设置。
- 点击下载记录的主要区域或任务菜单「任务详情」进入独立详情页，包含完整文件名、实时更新的大小/速度/ETA、最近进度回调、重试次数、下载方式、站点、错误原因及脱敏诊断报告。
- 单项删除由下载页面持有稳定的底部 Sheet，二次确认明确区分“永久删除本地文件和记录”及“仅移除记录”；左滑禁止全滑自动删除。删除关闭面板后按任务 ID 执行，避免 SwiftUI 销毁弹出源。
- “文件”变成独立栏目；展示 Downloads 文件夹真实内容，支持文件类型筛选、搜索、排序、预览、分享、重命名、批量选择和删除，包括旧版本的孤立文件。
- 浏览器主页增加收藏网站与最近访问、菜单收藏/取消收藏及历史查询；历史使用 UserDefaults 本地持久化，不保存 Cookie/密码/网页内容，设置中可清除历史。
- 设置中心集中管理下载模式、通知、网页深色模式及磁盘占用提示。任务诊断仅暴露下载网站域名，绝不导出完整带鉴权 token 的分享网址。
- 实时总速度只累加最近 18 秒内收到有效进度回调的任务，避免后台挂起时展示过期的速率；完成记录打开文件之前会再次确认文件存在。
- 图标沿用 1.9.4 新版浅色/深色资源。沿用原 Bundle ID、后台 URLSession、App Group、下载数据库和文件保存目录，通常可以覆盖安装保留数据。
- 不保证后台始终最高速度，仍需在实际 iPhone 上验证 20GB 长时间下载、左滑操作及分享扩展签名权限。

## 2.0.3 · 紧凑删除面板与 iOS 26 系统进度

- 下载删除确认面板重新设计：缩为自适应约 176–226pt，红色文本删除本地文件与记录、普通文字仅移除记录、右上角关闭；不再使用两块彩色大按钮和空白占位。
- iOS 26 及以上新增 `BGContinuedProcessingTask` 系统进度尝试：仅在用户前台主动开始下载时提交请求，以实际 URLSession 下载进度回调驱动系统 Progress；系统自身显示任务实时活动，避免与 App 原 ActivityKit 双重显示。

## 2.0.6 · URL 图标拖放实验版

- 主 App Info.plist 新增 `CFBundleDocumentTypes`，声明 `public.url` 网页链接作为可查看的文档类型，尝试使 iOS 主屏幕图标识别拖来的 URL；是否出现绿色＋由 iOS SpringBoard 决定，苹果文档未承诺第三方 App 与 Safari 完全一致。
- SwiftUI 主页面 `onOpenURL` 接收系统传来的 HTTP/HTTPS 链接，自动切换到内置浏览器，并打开 URL；同一链接连续拖入也会重新加载。
- 主 App `onDrop` 支持从其他 App 传来的 `public.url` / `public.plain-text`，拖入时提示“松手打开链接”，普通文本中也尝试识别网页 URL。
- 只接受 HTTP(S) 且必须有有效主机名，拒绝 javascript/data/file 等不应当直接打开的协议；不将分享页面误当成直接下载文件。
- 继续保留 iOS 分享扩展、原 App Group、灵动岛、后台传输引擎、下载任务数据与三栏界面。
- **真机测试**：长按 Safari/聊天链接 → 保持拖动回主屏幕 → 拖到后台下载图标 → 检查绿色＋与松手后的导航。如果图标无＋，属于平台对文档类型拖放的实际分发差异，App 内拖放和分享扩展仍可用。

## 2.0.7 · 修复图标拖放唤醒后链接没有打开

- 增加统一 URL 接收路由：`onOpenURL`、`onContinueUserActivity`、AppDelegate 的 URL/用户活动回调、App 启动参数、分享收件箱以及 App 内 `onDrop` 均将收到的链接送进同一个入口。
- 修复系统将网页位置作为 `file://` 文件交付时被旧版直接拒绝的问题。现在可解析受安全范围保护的小型 `.webloc` 属性列表、`.url` 快捷方式和文本 URL；拒绝无法解析或非 HTTP(S) 的内容。
- BrowserView 网页区域增加单独的拖放接收处理，降低 WKWebView 占据整个屏幕后根 TabView 接收不到 drop 的风险。
- 新增「设置 → 拖放诊断」，持久记录最近的事件名、输入类型与目标域名；不保存完整网址、签名参数或 Cookie，支持复制及清空。
- 支持相同链接连续拖入；对同一系统交付造成的近距离重复回调作短暂去重，避免重复开启网页。
- 实际主屏幕图标的绿色＋由 iOS 提供。若 App 能启动却仍无链接，诊断记录可定位是否根本没有收到系统事件，不能仅凭 Xcode 编译声称完全修复。

## 2.0.9 · 修复 public.url + public.utf8-plain-text 拖入后未打开

- 根据真机日志确认 `onDrop` 已获得 `public.url` 与 `public.utf8-plain-text`，旧版只读取第一种表示，解析失败便直接结束。
- 引入 DroppedLinkReader：在 `onDrop` 回调返回前同时启动 URL 对象、字符串对象、`public.url` 数据、`public.utf8-plain-text` 数据以及原始 URL 对象读取，任意一种成功即交给现有浏览器路由。
- 新增 DroppedLinkCodec，支持 UTF-8/UTF-16 网页链接、带说明文字的链接、.url 文本文件、XML/二进制 .webloc、NSKeyedArchiver NSURL 等实际表示，拒绝非 HTTP(S) 与过大数据。
- 诊断记录明确区分每一种读取方式，**只显示表示名称、数据大小和网站域名，不记录完整签名 URL**。
- 新增 macOS Foundation `NSItemProvider` 真正对象/数据模拟测试（NSURL、NSString、public.url 数据、无效 public.url + 有效文本回退），此项必须先通过，才会运行 iOS Release 构建。
- 仍需用户的 iPhone 真机将链接拖入页面验证：自动测试不能模拟 Safari 原生网页的全部数据提供方式，也不能证明主屏幕图标直接松手会将链接交给第三方 App。

## 2.1.1 · 图标拖放注册与多表示兜底

- 真机日志里的「无匹配数据」来自旧版只调用一次 `loadItem("public.url")`：跨进程提供方会用 `(nil, nil)` 结束这次请求，任何类型转换都拿不到内容。2.0.9 已改为并行读取全部声明表示，本次构建补齐剩余边界。
- 同一次拖放可能带多个项目：最多读取 4 项，任意一项解析出网页链接即打开，不再只检查第一项。
- 新增 3 秒兜底：某个表示始终不回调时，读取以空结果结束并写入诊断，界面不会毫无反应。
- 支持 `public.file-url` 原始对象，拖入 `.webloc` / `.url` 文件走同一解码器。
- 兼容以字典对象提供的 `.webloc`（`URL` 键）。
- 自动测试新增：多项目拖放、完全不回调的表示、字典对象。
- 真机上的图标拖放只打开 App、不打开链接，原因在系统路由而不在解析：网页链接按 URL 打开处理，浏览器（Chrome、Firefox）都只声明 `http` / `https` URL 方案，不声明 `public.url` 文档类型；文档类 App 才用 `CFBundleDocumentTypes`。此前本 App 只声明了文档类型，图标会亮、App 会开，但系统没有可用的 URL 处理声明。
- 本次在 `Info.plist` 新增 `CFBundleURLTypes` 的 `http` / `https` 方案，保留 `public.url` 文档声明以继续接受图标拖放。Swift 侧入口无需改动：`App 启动参数`、`AppDelegate openURL`、`Scene 冷启动`、`Scene openURLContexts`、`NSUserActivity` 都已接好。
- 平台边界：`com.apple.developer.web-browser` 由 Apple 审批，侧载无法取得。如果系统只把网页链接交给默认浏览器，这次构建的表现为「图标亮、App 开、没有链接」，诊断里的 URL 计数仍为 0。判定方式是装 2.1.1 后做一次图标拖放，再看「设置 → 拖放诊断」。
- 若计数为 0，改走 Safari 扩展按钮或快捷指令入口；仓库里已有 Safari 扩展的构建流水线。

## 2.1.2 · URL 类型补必需角色与反向域名

- 2.1.1 真机日志：图标拖放触发的是冷启动，`场景配置请求` 与 `Scene 冷启动` 的 URL、用户活动计数都是 0。系统只启动了 App，没有投递链接。
- Apple 的 `CFBundleURLTypes` 文档把 `CFBundleTypeRole` 标为必需键；2.1.1 缺这个键，URL 类型可能没有被 LaunchServices 接受。本次补 `Viewer`，并把 `CFBundleURLName` 改为反向域名 `com.example.backgrounddl.web`。
- 仍是判定版本：若计数继续为 0，说明 iOS 只把网页链接交给默认浏览器，侧载拿不到 `com.apple.developer.web-browser`，图标拖放到此为止，改走 Safari 扩展按钮。

## 2.1.3 · App 内任意页面接收拖放

- 2.1.1 与 2.1.2 的真机结论：未设默认浏览器的 Chrome 也能接住图标拖放；Chrome、Firefox 的 App entitlements 都带 `com.apple.developer.web-browser`。这是 Apple 审批的 managed entitlement，个人侧载 profile 里没有，图标拖放对侧载 App 走不通，后续不再加 plist 键。
- App 内拖放改为窗口级 `UIDropInteraction`：挂在 host window 上，浏览器、下载、设置三个 tab 的任意位置都能接住链接。原来的 TabView 级 `.onDrop` 覆盖不到设置表单和下载列表的滚动视图。
- 解析仍走 `DroppedLinkReader`；失败照旧写入「设置 → 拖放诊断」并弹窗。

## 2.1.4 · 对齐 Via 的 URL 注册

- 拆开同一证书签名的 Via 1.9.0 IPA：entitlements 只有 `application-identifier`、`team-identifier`、iCloud 容器和 `aps-environment`，没有 `com.apple.developer.web-browser`；Info.plist 没有 `CFBundleDocumentTypes`，`CFBundleURLTypes` 是 http / https / viabrowser 加 `CFBundleTypeRole = Editor`。
- 结论：图标拖放不需要 web-browser entitlement，之前的判断错了。差别在注册：2.1.2 多了 public.url 文档类型，URL 角色用了 Viewer。
- 2.1.4 对齐 Via：删掉 `CFBundleDocumentTypes`，`CFBundleURLTypes` 改为 Editor，`CFBundleURLName` 用 bundle id，schemes 增加 `backgrounddl`，后续 Safari 扩展或快捷指令入口可直接用。

## 2.1.5 · 撤回窗口级拖放，恢复页面内接收

- 2.1.3 把拖放挂到 host window 的 `UIDropInteraction` 上，结果它抢走拖放却不投递，App 内拖放全部失效。这是回归，撤回。
- 恢复 TabView 级 `.onDrop` 和浏览器页原有接收；设置页的 `Form`、下载页的 `List` 和根视图各自加 `.onDrop`，覆盖滚动区域。
- 图标拖放的注册保持 2.1.4 不变。

## 2.1.6 · 根视图拖放与全局落点提示

- 2.1.5 在 `Form` / `List` 上直接加 `.onDrop` 仍收不到：这两个页面的滚动视图自己持有命中测试，SwiftUI 的拖放修饰器没有机会接管。
- 改回 UIKit，但这次挂在 `window.rootViewController.view` 上。它是三个 tab 的共同祖先，下载页和设置页都在它下面；不是 2.1.3 那个无效的 UIWindow。
